# 文档检查与归档

用于集中检查、合并整理或归档现有 docs，不用于单篇文档的普通更新。

## 检查步骤

1. 统计文档数量、目录层级和篇幅，识别版本目录、开发者目录和缺失索引。
2. 将内容归类为项目导览、架构、复杂功能、接口或数据规则、外部资料、重复内容或过期内容。
3. 标出代码复述、重复 Schema、实现步骤、版本流水账、与代码不一致的说明和失效链接。
4. 在移动、合并或删除前，列清每份旧文档要移到哪里、合并到哪里或为什么删除。
5. 合并仍然适用的决定和规则；可从代码、Schema、需求单或 Git 恢复的细节不迁移。
6. 更新 docs/README.md、相对链接、状态和核验日期。

没有要求集中重构时，只整理本次涉及的文档；明确要求重构指定范围时，再按已经确认的去向处理。

## 两类归档

### 已失效文档

只有失效内容仍能解释重要决策或迁移时才归档。归档说明不保留旧实现教程：

```markdown
---
title: <旧主题>
type: archive
status: archived
last_verified: YYYY-MM-DD
ai_read: history-only
---

# <旧主题>

> 替代文档：<仓库相对路径>

说明为什么失效、哪些历史决定仍值得保留，以及现在去哪里查看有效说明。
```

没有历史价值的重复内容直接删除；编辑历史由 Git 保存。

### 版本开发归档

一个版本确实留下兼容、迁移、回滚或后续演进需要知道的决定时，可建立 `docs/archive/versions/v<version>.md`。它不是需求全集、版本快照或发布流水账；当前行为仍由代码和 `active` 文档说明。

AI 从产品原型整理出的当前需求基线，以及开发中仍在使用的解决方案，继续放在 `features/`，不能直接移入版本归档。版本结束时只提炼下面这些长期结论；原型解析的中间输出如果没有独立维护价值，应删除或留在原始产品资料中。

只保留：

- 这个版本改变了哪些长期行为或边界，以及为什么这样决定。
- 与旧版本并存时必须遵守的兼容、迁移或回滚条件。
- 发布后仍需关注、且会影响后续开发的已知限制。
- 对应当前文档、稳定测试或提交的少量相对链接。

不要复制页面清单、完整接口、原型文案、Bug 列表、测试输出或当前功能文档。没有上述内容时不建归档，Git 和发布记录已经足够。

```markdown
---
title: <产品名> <版本> 开发归档
type: archive
status: archived
last_verified: YYYY-MM-DD
ai_read: history-only
---

# <产品名> <版本> 开发归档

## 这个版本留下了什么

只写会影响后续维护的行为变化和决定原因。

## 兼容、迁移与回滚

只写当前仍需遵守的条件；没有则删除本节。

## 现在去哪里看

链接到当前有效文档或稳定验证依据。
```

版本归档统一使用 `history-only`。会议纪要、团队复盘、经验分享和纯协作材料不属于项目文档，不进入 `docs/archive`。
