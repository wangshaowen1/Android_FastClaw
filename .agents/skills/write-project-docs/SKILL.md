# 项目文档

只记录长期有用、又无法直接从代码看出的信息。文档是否有价值，看它能否讲清关键决定并帮助查找，不看篇幅和覆盖率。

## 1. 判断是否需要文档

只有符合下面任一情况时，才新建或保留项目文档：

- 定义架构、多个模块共同遵守的接口或数据规则、持久化模型，或者多个功能必须共同遵守的规则。
- 跨模块或跨端，或者存在复杂状态机、异步、并发、生命周期、迁移、兼容、回滚、安全、隐私、支付或性能风险。
- 需要跨功能或跨端解释稳定业务页面、视图容器、功能入口、公共路径、导航来源或拦截规则。
- 存在多个合理方案，后续维护者需要理解选型依据。
- 预计跨版本迭代，或需要交接给其他开发者。
- 误解设计造成的成本明显高于维护文档的成本。

文案修改、样式微调、简单跳转、局部 Bug，以及沿用现成做法、步骤很简单的需求不建立文档。会议纪要、团队复盘、经验分享和纯协作说明也不属于项目文档，不进入 `docs`。不满足上述条件时，简短说明原因即可。

## 2. 先确认必要事实

1. 文档维护任务先读 `docs/README.md`；普通开发任务只在索引明确指向或缺少必要背景时读取它，不把 docs 当作默认上下文。
2. 通过索引和 `rg` 定位当前领域，首轮只读一份与任务直接相关的文档，不预读整个 docs，也不因为正文存在链接就逐篇展开。
3. 当前文档只在索引或当前任务选中后读取；标为 `history-only` 的归档只用于版本比较、回归、迁移、回滚或追溯决策。
4. 只读取足以核实方案的代码、接口或数据规则和测试；代码能证明现在怎么实现，不自动代表最终方案。
5. 把现状、已确认要达到的结果和完成情况分开写。尚未确认且会改变方案的内容放入“还需要确认什么”，不要当成既定方案。
6. 已有目录能放下这些文档时继续沿用，不要为了套模板重排目录。

## 3. 确定位置和文档类型

新仓库默认使用以下目录结构：

```text
docs/
├── README.md                  # 项目导览和文档索引
├── architecture/
│   └── <topic-slug>.md        # 长期职责和必须遵守的规则
├── features/
│   ├── <feature-slug>.md      # 默认：需求和方案合并维护
│   └── <complex-feature>/     # 仅当需求和方案需要独立维护
│       ├── README.md          # 当前需求基线和功能入口
│       └── solution.md        # 可选：复杂解决方案
├── contracts/                 # 可选：多个模块或系统共同遵守的接口或数据规则
│   └── <contract-slug>.md
└── archive/                   # 不再代表当前事实、但仍有追溯价值的文档
    └── versions/
        └── v<version>.md      # 可选：一份版本开发归档，不复制当前文档
```

- 默认不要增加多层目录；只有同一主题存在多份可独立阅读的文档或本地资源时，才增加主题目录。
- 功能文档默认使用 `features/<feature>.md`。只有当前需求基线和解决方案都需要独立维护时，才改用 `features/<feature>/README.md` 与可选的 `solution.md`；两份文档不得重复正文。
- 路径使用稳定的英文小写 `lower-kebab-case`。
- 当前文档的目录不使用版本号、开发者或实现阶段；版本号只允许出现在 `archive/versions/v<version>.md` 的文件名中。
- 只使用仓库相对链接和相对代码路径，不记录任何开发机器绝对路径。
- 同一功能跨版本迭代时更新原文档，不按版本、开发者或实现阶段复制当前文档。版本归档只记录无法从 Git 直接看懂、且对兼容、迁移、回滚或后续演进仍有价值的差异和原因。
- AI 从产品原型整理出的需求基线和开发中的解决方案属于当前功能文档，不得直接写成版本归档。版本结束后只把仍影响兼容、迁移、回滚或后续维护的结论提炼到归档。

先确定文档类型，每次只读取对应参考；不要加载其他模板：

- docs/README.md：读取[项目导览模板](references/overview.md)。
- 长期系统或业务域边界：读取[架构模板](references/architecture.md)。
- 需要跟着代码持续更新的复杂功能，或需要判断需求与方案是否拆分：读取[复杂功能模板](references/feature.md)。
- 多个模块或系统共同依赖的接口、事件或数据规则：读取[接口与数据规则模板](references/contract.md)。
- 集中检查、合并整理、废弃旧文档或建立版本开发归档：读取[文档检查与归档流程](references/audit-and-archive.md)。

当前文档使用以下元数据：

```yaml
---
title: <标题>
type: overview | architecture | feature | contract
status: draft | active | deprecated
last_verified: YYYY-MM-DD
---
```

当前文档不填写 `ai_read`，由 `docs/README.md` 或当前任务选中后才读取，不代表 AI 默认加载。

归档文档使用 `type: archive`、`status: archived`，并明确填写 `ai_read: history-only`。复杂功能增加 `implementation: planned | in-progress | complete`；只有确实需要说明适用版本、平台或范围时才增加 `applies_to`；废弃文档通过 `replacement` 指向替代文档。

## 4. 写清楚并保持精简

- 面向开发者的标题和正文优先使用读者能直接理解的表达；只有便于查找代码或避免歧义时才保留技术术语，并在首次出现时简短说明。
- 模板里的章节只是提示，不是固定目录。范围直接写实际内容，不在下面再套空的正反标签；标题应直接说明读者能得到什么，不要照抄含义不清的模板词。
- 不要为了结构对称保留空标题、空列表或只有一句套话的章节；可选章节没有实质内容时直接省略。
- 根据主题，只记录目标、范围、职责、状态由谁维护、主要流程、必须遵守的规则、设计原因、出错后的处理和验证依据。
- 只引用少量稳定的模块、包、入口、Schema 或测试位置，不记录行号和完整文件清单。
- 导航主题只记录稳定的业务页面、视图容器或功能入口，以及公共路由、URL、跳转目标或事件目标的职责、必要输入、来源和限制；只有确实存在平台差异时，才在表里增加平台一列。
- 图或表必须比文字更短、更清楚；简单线性流程直接使用文字。

以下内容应删除或改为链接：

- 按类、方法、页面或字段逐项讲解；介绍跨功能或跨端导航时，可以列稳定业务页面、视图容器或功能入口，但不得扩展为平台类、组件树或普通内部跳转清单；
- 穷举当前已有功能、接口或文件；
- 已有明确来源的完整 API Schema；
- 写给 AI 的逐步编码指令；
- 在多篇文档中重复的全局规则、验收标准和背景；
- 重复 commit 内容的 Changelog；
- 与当前方案无关的远期设想。

只给出建议最多行数，不设最低行数：

| 类型 | 建议最多行数 |
| --- | ---: |
| 项目导览 | 180 行 |
| 复杂功能 | 250 行 |
| 架构文档 | 350 行 |
| 接口与数据规则 | 400 行 |
| 归档说明 | 80 行 |

超过建议长度时，先删除可从代码、Schema、需求资料或 Git 恢复的细节，再考虑拆分。只有子主题会单独长期维护，或经常需要被单独引用时才拆分文档。

## 5. 维护状态并保持一致

- `draft`：讨论稿，不作为编码依据。
- `active`：已经确认，可作为目标和决定的依据。
- `deprecated`：仅保留历史背景，必须指向替代文档。
- `archived`：不代表当前实现，只用于指定的历史追溯场景。

- 用代码判断现在怎么实现，用 `active` 文档判断已经确认的目标。
- 归档不能覆盖当前代码或 `active` 文档；需要恢复历史方案时，也必须先核对当前分支。
- `implementation: complete` 与代码冲突时，必须明确报告差异，不能自行忽略文档或代码的一方。
- 影响行为的代码与文档在同一次变更中更新。
- 只有核对相关代码、接口或数据规则和测试后才能更新 `last_verified`。
- 编辑历史交给 Git；正文只保留无法从 diff 还原的关键决策原因。
- 新建、重命名或废弃当前文档时，同步更新 docs/README.md 索引。版本归档由导览中的目录路由统一查找，不逐个列出；只有需要提醒所有开发者的关键版本才单独加入索引。
- 项目有全局导航说明时，公共路由或 URL、服务端或通知跳转、入口拦截或稳定页面职责发生变化，应在同一次变更中更新说明。

## 6. 验证

运行固定检查脚本：

```text
python <skill-dir>/scripts/audit_docs.py <repository-or-docs-path>
```

长度或文件名超出建议值时只给警告；缺少必需元数据、相对链接失效和包含机器绝对路径属于错误。

完成前确认：

- docs/README.md 能引导开发者和 AI 找到完成任务所需的最少文档。
- AI 的读取条件明确；普通任务不会误读 `history-only` 归档。
- 文档能回答当前主题管什么、应以哪些代码、配置或外部资料为准、关键状态或流程、出错后怎么处理以及如何验证。
- 导航内容能帮助读者从业务页面或公共入口找到最少必要资料，并且没有把平台实现清单复制进正文。
- 现状、已确认方案和完成情况与证据一致。
- 正文没有大段代码复述、重复 Schema、实现步骤清单或版本流水账。
